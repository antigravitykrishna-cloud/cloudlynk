## 2. Ship-Blockers (must fix before any user touches production)

### 🚨 BLOCKER 1: Channel post insert hangs (the bug you're debugging now)

**Where:** `lib/posts.ts` lines 129–198, `createPost`
**Symptom:** 5-minute spinner after Cloudflare upload completes; row eventually appears (or doesn't)
**Root cause (refined after the dev's logcat):** the `.insert().select('*, author:profiles!channel_posts_author_id_fkey(id,full_name,avatar_url)').single()` chain — specifically the FK-embed hint + the `Accept: application/vnd.pgrst.object+json` header that `.single()` sets. PostgREST is either taking 5 min to plan/execute, or the embed join is hitting a slow path. The dev is instrumenting to confirm which.

**Fix (proposed, pending logcat):**
```ts
const ac = new AbortController();
const timer = setTimeout(() => ac.abort('insert-timeout'), 30_000);
try {
  const { data, error } = await supabase
    .from('channel_posts')
    .insert({...})
    .select('id, channel_id, author_id, title, body, content_type, status, video_url, created_at')
    .abortSignal(ac.signal)
    .maybeSingle();
  if (error) throw error;
  return data as ChannelPost;
} finally { clearTimeout(timer); }
```

**Bigger fix (recommended):** rewrite the insert as a Postgres function and call it via `supabase.rpc()`. RPCs are planned once, executed in one round-trip, can't get stuck in PostgREST embed parsing. This is the "I never want to debug this again" solution.

**Verify:** rebuild debug APK, install on AVD, repeat Test 5, see the row within 5s + success alert.

### 🚨 BLOCKER 2: IAP upgrade is self-issuable — anyone can get premium for free

**Where:** `app/(tabs)/_layout.tsx` lines 53–84 (`onPurchaseSuccess`) and `hooks/useAuth.ts` (profile update via `supabase.from('profiles')`)

The flow is:
1. User taps "Get Premium" → `requestPurchase` opens Google Play sheet
2. `onPurchaseSuccess` fires → calls `supabase.from('profiles').update({plan: 'premium', storage_limit: ..., can_upload_content: true}).eq('id', user.id)`
3. The user is now premium

**The hole:** Step 2 is a plain `update` against the user's own profile, which the RLS policy `"Users can update own profile"` allows. **There is no server-side receipt verification.** A user (or a script with their JWT) can call this same update directly and get premium without paying. Anyone with the anon key + a valid session JWT can do this from curl:

```bash
curl -X POST 'https://wdtwjiixuueqejfraaod.supabase.co/rest/v1/profiles?id=eq.<their_id>' \
  -H "apikey: <anon>" -H "Authorization: Bearer <jwt>" \
  -H "Content-Type: application/json" \
  -d '{"plan": "premium", "storage_limit": 214748364800, "can_upload_content": true}'
```

**Fix:**
1. Move the `plan` write to a **server-side function** that takes a verified Google Play purchase token as input, calls Google's API to verify it, then updates the profile. Disable the client-side update path.
2. Tighten the profiles RLS — `plan`, `storage_limit`, `can_upload_content`, `is_admin`, `role` should NOT be user-updatable. Only `full_name`, `avatar_url`, `auto_backup`, `wifi_only`, `notifications_enabled` should be in the `WITH CHECK`.

```sql
-- Replace the current "Users can update own profile" policy
create policy "Users update safe profile fields only"
  on public.profiles for update
  using (auth.uid() = id)
  with check (
    auth.uid() = id
    and plan = (select plan from public.profiles where id = auth.uid())  -- unchanged
    and storage_limit = (select storage_limit from public.profiles where id = auth.uid())
    and can_upload_content = (select can_upload_content from public.profiles where id = auth.uid())
    and is_admin = (select is_admin from public.profiles where id = auth.uid())
  );
```

**Severity:** Critical. This is free-tier bypass. Any user can become premium.

### 🚨 BLOCKER 3: Migration state is corrupted

**Where:** `supabase/migration_v8.sql` was never fully applied — `profiles.username` column doesn't exist (verified earlier in this session).

**Consequence:**
- Anything that reads or writes `profiles.username` (the trigger in v8, future feature work) fails
- The plan enum check constraint is still in the OLD state ('free', 'pro', 'enterprise') per the original `schema.sql` line 22, so any INSERT with `plan = 'standard'` (e.g., IAP upgrade) blows up
- `supabase_migrations.schema_migrations` table is missing — the migration tracker is broken

**Fix:**
1. Run `supabase/migration_v8.sql` in the Supabase SQL Editor (drops old plan check, adds `username`, adds normalized constraint)
2. Run `supabase/migration_v9_plan_fix.sql` (repair, idempotent)
3. Verify: `select column_name from information_schema.columns where table_name = 'profiles' and column_name = 'username';` → 1 row
4. Verify: `select distinct plan from public.profiles;` → only 'free', 'standard', 'premium'

**Don't ship without this.** Otherwise, the IAP "fix" you do for Blocker #2 will hit the same constraint failure your earlier IAP work hit.

## 3. Significant Quality Issues (will bite within 1-2 months)

### Issue 4: Database types are hand-written, will drift

**Where:** `lib/supabase.ts` lines 95–269 — the `Database` type is hand-maintained (269 lines of types)

This is fragile. Every time you add a column, an enum value, or a table, you have to remember to update this. The build won't fail when it drifts. You'll only find out at runtime via TypeScript casts like `as ChannelPost` or `(profile as any)?.is_admin` (which appears 4+ times in the code — sign #1 of drift).

**Verify it's drifting:** the `Database['public']['Tables']['profiles']` type does NOT include `username`, `is_admin`, `can_upload_content`, `role`, `creator_status`, `fcm_token`, `auto_backup`, `wifi_only`, `notifications_enabled` — all of which exist in the actual DB. So the type is **already wrong**, you're just casting around it.

**Fix:** generate types from the live DB:
```bash
supabase gen types typescript --project-id wdtwjiixuueqejfraaod --schema public > lib/database.types.ts
```
Wire it into CI. Hand-written types for a Supabase project is a code smell at any size.

### Issue 5: ESLint is functionally disabled

**Where:** `eslint.config.js` lines 17–55

`eslint-plugin-react` is incompatible with ESLint 10, so 23 react/* rules are turned off wholesale. `react-hooks` is also missing 4 important rules. The TS and import rules still work, but anything React-specific — jsx-key, prop-types, no-direct-mutation-state — silently doesn't enforce.

**This is why the `as any` casts in `profile.tsx` line 150, 200, 230, etc. exist.** No lint to catch them.

**Fix:** either downgrade to ESLint 9 (lose nothing critical), or pin a working version of `eslint-plugin-react`. Until then, ESLint is running but giving false confidence.

### Issue 6: Sign-up race + double-insert

**Where:** `hooks/useAuth.ts` lines 45–67, `signUp`

The flow:
1. `supabase.auth.signUp({...})` — fires the `handle_new_user` trigger → creates a profile row with the email prefix as `username`
2. Then `useAuth.signUp` also calls `supabase.from('profiles').insert({...})` with the same data

Step 2 is redundant. The trigger already created the row. The `ON CONFLICT (id) DO NOTHING` saves it from erroring, but the user's `full_name` in the manual insert is the one they typed, while the trigger's `username` is the email prefix. Two different fields, written from two different sources.

**Side effect:** if email confirmation is required (Supabase default), the trigger fires immediately on signup, so the user has a profile before they verify. Then `useAuth` tries to insert a duplicate profile with the typed `full_name`. If they later set a different full_name, the trigger's `full_name` is the email prefix, and the manual insert is "their" full_name. With `ON CONFLICT DO NOTHING`, the manual insert is dropped. **The user's typed full_name never makes it into the DB.**

**Fix:** delete the manual insert block in `signUp` (lines 50–66). The trigger handles it. If you need to set `full_name` from the typed input, add a follow-up `update` after the trigger fires (or better: pass it via `auth.signUp({options: {data: {full_name}}})` so the trigger picks it up).

### Issue 7: Silent error swallowing

**Where:** multiple files, consistent pattern

| File | Line | Code | What's lost |
|---|---|---|---|
| `lib/posts.ts` | 156–160 | `try { mediaUrl = await uploadMedia(...) } catch { mediaUrl = null; }` | Thumbnail upload failure → post still creates without thumbnail, user never knows |
| `lib/posts.ts` | 161–167 | `try { thumbnailUrl = await uploadMedia(...) } catch { thumbnailUrl = null; }` | Same |
| `lib/posts.ts` | 250–257 | `try { ... } catch { /* Silently fail — notifications are non-critical */ }` | (Actually correct here, but pattern bleeds) |
| `app/(tabs)/channels/index.tsx` | 70 | `console.error('createChannel error:', JSON.stringify(err))` — and the `Alert.alert` shows `err.message ?? JSON.stringify(err)` | User sees JSON in error toast |
| `hooks/useFiles.ts` | 69, 115 | `catch { setActiveTransfers(prev => prev.map(... status: 'failed' }))` | No log, no message, failed transfer just sits there |
| `app/(tabs)/channels/[id].tsx` | 50 | `Alert.alert('Error', err.message);` in `useEffect` load | First-paint error toast every time the screen fails to load |
| `lib/storage.ts` | ~210 | `if (error) throw error;` (this is fine) | — |

**Pattern:** errors get swallowed with no surface, no log, no telemetry. The user can't report what happened because nothing tells them. The dev can't diagnose because there's no log.

**Fix:** add a single utility:
```ts
// lib/errors.ts
export function reportError(scope: string, err: unknown, opts?: { silent?: boolean }) {
  const msg = err instanceof Error ? err.message : String(err);
  console.error(`[${scope}]`, msg, err);
  if (!opts?.silent) {
    // surface to UI
  }
}
```
Use it everywhere. Telemetry next (Sentry/Datadog) is a one-liner.

### Issue 8: No storage quota enforcement

**Where:** `lib/storage.ts` lines 75–148, `uploadFile`

The function uploads a file, inserts the row, then calls `increment_storage_used`. But **it never checks if the user has enough quota first.** A free-tier user (15 GB) can upload 100 GB; the storage_used counter will just go past the limit, and the UI bar will overflow (>100%). The `storage_limit` field is for display only — nothing blocks the upload.

**Fix:** add a check at the top of `uploadFile`:
```ts
const { data: profile } = await supabase.from('profiles').select('storage_used, storage_limit').eq('id', userId).single();
if ((profile?.storage_used ?? 0) + fileSize > (profile?.storage_limit ?? 0)) {
  throw new Error('Storage limit reached. Please upgrade your plan.');
}
```
Even better: move this into a `check_storage_quota(userId, fileSize)` RPC that the file upload pipeline calls first.

### Issue 9: `getMyChannels` + `getDiscoverChannels` are N+1-shaped

**Where:** `lib/channels.ts` lines 38–66, `app/(tabs)/channels/index.tsx` lines 30–44

`getMyChannels` fetches `channel_members` with the `channels(*)` embed. For a user in 50 channels, that's one query. Good.

But `index.tsx`'s `loadChannels` does:
```ts
const [mine, discover] = await Promise.all([
  ChannelService.getMyChannels(user.id),
  ChannelService.getDiscoverChannels(user.id),
]);
```
Two sequential-ish queries, fine. The bug is in the filter:
```ts
const filteredDiscover = discoverChannels.filter(
  ch => !myChannels.some(mc => mc.id === ch.id)
);
```
O(n*m). For small numbers (n=20, m=20), this is fine. If either grows, it doesn't scale. **Not a blocker**, just note for later.

### Issue 10: `RootLayout` console.log ships to production

**Where:** `app/_layout.tsx` lines 16, 19, 21, 25, 28

Every render logs `'RootLayout rendering... loading: ... session: ...'`. Every navigation logs again. In production builds, this fills up logcat for every user, exposes session state, and slows the app.

**Fix:** wrap in `__DEV__`:
```ts
if (__DEV__) console.log('RootLayout useEffect. loading:', loading, 'session:', session ? 'exists' : 'null', 'segments:', segments);
```
Same for any other `console.log` in `useNotifications.ts` and elsewhere.

### Issue 11: `useUsageTimer` has an off-by-one on the 30-min threshold

**Where:** `hooks/useUsageTimer.ts` line 69

```ts
const minutesUsed = Math.min(30, Math.floor(usedMs / 60000));
const minutesLeft = Math.max(0, 30 - minutesUsed);
```

If `usedMs = 29:59.999` (29 min 59.999 sec), `minutesUsed = 29`, `minutesLeft = 1`. UI shows "1 min left". At exactly 30:00.000, the `setShowPaywall(true)` from the save logic fires, so the paywall pops. But the display still shows 29 min / 1 min left for a frame. Cosmetic.

Worse: `Math.min(30, ...)` caps at 30, so `minutesLeft` is 0 once the threshold fires. OK. But the *display* on the profile screen if you build one would be off-by-one at the boundary. **Verify before shipping** — show the actual minutes used in the paywall hero (currently it shows "free 30 min" hardcoded).

## 4. Code Smells & Maintainability Issues

### 12: `app/(tabs)/channels/[id].tsx` is 814 lines, does too much

**What it contains:** the entire channel detail page, the detail modal (with video player), the create-post modal, the genre picker modal, the channel content grid, the join flow, the hero section, the "pending review" section, the "creator locked" banner. All in one file.

**Fix:** split into:
- `app/(tabs)/channels/[id].tsx` — page-level layout + data load (≤150 lines)
- `components/channel/ChannelHero.tsx`
- `components/channel/ContentCard.tsx`, `GenreRow.tsx`
- `components/channel/DetailModal.tsx`
- `components/channel/CreateContentModal.tsx`
- `components/channel/GenrePickerModal.tsx`

This is a maintainability crisis waiting to happen. The next feature will push it past 1000 lines.

### 13: The "I forget what state I'm in" pattern in modals

`CreateModal` in `[id].tsx` has 11 separate `useState` calls. No form library. When a user partially fills the form, then closes the modal, then re-opens, the state is reset (by `reset()`) — which is intentional, but the bug is that `reset()` only fires after a successful submit, NOT after a cancel or close. So the partial state lingers in the parent.

Wait, let me re-read… `handleCancel` calls `reset()` then `onClose()`. OK. So cancel does reset. But the **Modal's `onRequestClose` calls `handleCancel`**, but the parent only re-renders the modal when `showCreate` flips. So if the user closes via the system back gesture on Android, the modal hides but the parent state is reset. The next time they tap + Add Content, it's a fresh form. Good.

But the `GenrePickerModal` uses `useState` for the selected genre separately. When the user picks a genre in the picker, it sets local state and calls onSelect — but the picker's local state doesn't sync with the parent's `genre` state. If the parent resets the form, the picker's local state stays. **Verify this** — could be a real bug where the picker shows a different selected genre than the form.

### 14: `useIAP` initialized in the layout fires on every tab render

`app/(tabs)/_layout.tsx` lines 53–84: the `useIAP` hook is called once (because it's in the layout), but the callbacks inside it (`onPurchaseSuccess`, `onPurchaseError`) close over state that might be stale. The hook's docs say callbacks are stable, so this is probably fine, but the IAP connection is initialized as soon as the tabs mount, even on screens that don't need it (Files, Home, Profile). For an empty app on first launch, this is wasted IAP setup.

**Fix:** initialize IAP lazily when the paywall first opens. Or accept the cost (it's small).

### 15: Inconsistent use of "platform-specific" pickers

- File upload: `expo-image-picker` with `mediaTypes: ['images', 'videos']`
- Post thumbnail: `expo-image-picker` with `mediaTypes: ['images']`
- Channel video: `expo-document-picker` with `type: 'video/*'`

The choice of document picker for video was a real fix (per the memory note about MediaStore crashing on videos >~10s). But it's a code smell that the same conceptual operation (upload media) goes through two different libraries based on the destination. Consider wrapping in a `pickers/media.ts` that exposes one API.

### 16: The `SettingsRow` component was moved module-level (good), but the dev tools block is hard-coded

`app/(tabs)/profile.tsx` lines 233–266 — the DEV TOOLS section is inline JSX, not a component. It's guarded by `__DEV__`, which is correct, but if you add more dev tools (e.g., a SQL console, a network inspector), this will get unwieldy. Extract to `components/dev/DevToolsPanel.tsx`.

### 17: `CATEGORY_ICONS, CATEGORY_COLORS, CATEGORY_DIM` are re-exported from `lib/storage.ts`

`lib/storage.ts` line 228 re-exports constants from `constants/theme.ts`. Half the codebase imports from `lib/storage`, the other half from `constants/theme`. **Pick one and stick with it.** The duplication is intentional-but-confusing.

### 18: `useEffect` cleanup leaks on rapid navigation

Multiple screens (`useNotifications`, `useFiles`, `useUsageTimer`, `useAuth`, `useFiles`, `useAcquisitionSource`) have `useEffect` with `[]` dep that opens a subscription / starts a timer. If the screen unmounts during a heavy operation, the cleanup *should* cancel it. Most do, but:
- `useAcquisitionSource.ts` — if the AsyncStorage read takes 200ms and the component unmounts before, `setSource` is called on unmounted component (React warning, not crash)
- `useFiles.ts` — the XHR upload in progress isn't aborted on unmount; the file might finish uploading but the callback hits a dead component

Neither is critical. But the latter could lead to a "ghost" upload — file in storage, no UI to show it. Worth a fix eventually.

### 19: `(profile as any)?.is_admin` is everywhere

Counted 4 uses. The Database type is missing `is_admin` (see Issue #4). Fix the types, delete the casts.

### 20: `expo-image-picker` flow on `lib/storage.ts` line 50 vs `lib/posts.ts` line 250

`StorageService.pickImage` returns the first asset only:
```ts
if (result.canceled) return null;
return result.assets[0];
```
But the picker is called with `allowsMultipleSelection: true`. So if the user picks 3 images, only the first is uploaded. **Bug or feature?** Document it. If bug, loop over `result.assets`. If feature, set `allowsMultipleSelection: false`.

### 21: `lib/storage.ts` has unused code: a `decode()` function was removed but a comment references it

`lib/storage.ts` line 225: `// decode() removed — no longer needed after switching to XHR FormData upload`

This is dead-comment archaeology. Delete the comment.

### 22: `lib/channels.ts` `createChannel` doesn't use a transaction

```ts
const { data: channel, error } = await supabase.from('channels').insert({...}).select().single();
if (error) throw error;

await supabase.from('channel_members').insert({...});  // ← if THIS fails, orphan channel
```

If the second insert fails (e.g., RLS rejects), the channel exists but has no members. The owner can't access it because `Members can view private channels` requires a `channel_members` row, AND `Owners can view their channels` was added in migration v4 specifically to fix this exact problem.

**Fix:** wrap in a Postgres function, or use a single RPC. The current code is a time bomb.

### 23: `useNotifications` realtime channel is per-user but unstable across sessions

`hooks/useNotifications.ts` line 34:
```ts
const channel = supabase
  .channel(`notifications:${userId}`)
  ...
```

Each mount creates a new realtime channel. If the user navigates to the notifications screen, then back, then again, three channels are open. Supabase's realtime auto-cleans stale ones, but it's wasteful and can show "ghost" updates.

**Fix:** move the channel to a singleton (e.g., `NotificationService.subscribe(userId)`) that returns an unsubscribe function. Reuse across mounts.

### 24: The `useUsageTimer` saves on background but loses on crash

If the app process is killed while in foreground (low memory, force-stop), the elapsed time since the last `saveElapsed` is lost. With a 60s save interval, max loss is ~60s. Acceptable. But the timer uses `Date.now()` for the session start, which is vulnerable to system clock changes (rare but real on Android).

## 5. Security Concerns

### 25: IAP bypass (covered as Blocker #2)

### 26: No rate limiting on auth endpoints

The `signIn` / `signUp` calls in `useAuth.ts` have no client-side throttling, no captcha, no rate limit. Combined with Supabase's default rate limits (which are generous for free tier), this is a brute-force target. Supabase has some built-in protections, but add a `supabase.rpc('check_auth_rate_limit')` if you care.

### 27: `useAuth.ts` exposes `signOut` but doesn't clear local caches

`signOut` just calls `supabase.auth.signOut()`. The in-memory `profile`, `files`, `notifications`, `feedPosts` etc. are all in React state and clear on next mount, BUT:
- The SecureStore JWT is cleared by supabase-js
- AsyncStorage keys (`streamly_usage_ms`, `streamly_acquisition_source`) are NOT cleared

So a user can sign out, another user signs in, and the second user inherits the first user's usage timer and acquisition source. Privacy leak, minor data leak.

**Fix:** on `signOut`, clear all app-local keys:
```ts
async function signOut() {
  await AsyncStorage.multiRemove(['streamly_usage_ms', 'streamly_acquisition_source']);
  await supabase.auth.signOut();
}
```

### 28: `getMyChannels` returns channels regardless of `is_public`

A user querying their own `channel_members` gets back the `channels` row even if the channel is private and they're not the owner. If they're a member, they should see it. If they're NOT a member (orphaned membership, or someone added them then removed them but the row lingers), they'd still see it. The RLS `"Owners can view their channels"` ensures owner-sees-own, and `"Members can view private channels"` ensures member-sees-theirs. But the JOIN in `getMyChannels` returns channels based on `channel_members` membership only — there's no check that the channel still exists. The `referencedTable: 'channels'` order is fine, but a deleted channel with a leftover member row would surface as null. Mostly fine, edge case.

### 29: `notifications.tsx` line 26-31: `handleTap` checks `notif.channel_id` and pushes, but if the channel was deleted between notification creation and tap, the push will fail silently

This is a minor UX bug. If admin approves a channel, then deletes it, then the user taps the notification, the channel page tries to load and errors. The `load()` in `channels/[id].tsx` already handles this (shows error alert), so not a crash, but ugly.

### 30: Edge function `generate-stream-upload` has no per-user rate limit

A user can hit the edge function 1000 times, getting 1000 Cloudflare direct-upload URLs, uploading 1000 GB, and then abandoning the inserts. The Cloudflare storage accumulates garbage.

**Fix:** track per-user pending uploads in a table, reject if >5 in flight.

### 31: Edge function trusts `can_upload_content` from the client

```ts
const { data: profile } = await supabaseClient
  .from("profiles")
  .select("can_upload_content, role")
  .eq("id", user.id)
  .single();

if (profileError || !profile?.can_upload_content) {
  throw new Error("User does not have upload permissions");
}
```

This is actually a CORRECT pattern — server-side check. Good. But `can_upload_content` is user-updatable (see Blocker #2). Fix that and this is fine.

## 6. Performance Concerns

### 32: `app/(tabs)/index.tsx` (Home) runs 4 parallel queries on every mount

`load()` calls `loadFiles`, `refreshProfile`, `getHomeFeed`, and `getAdminPendingCount` in parallel. If the user has 50 channels and 1000 posts, `getHomeFeed` does 2 round-trips (members + posts), `getAdminPendingCount` does 2, `loadFiles` does 1. That's 5+ round-trips on every home tab open. Not a "fix this" issue, but with React Query / SWR + a stale-time, the home screen would feel instant on subsequent visits.

### 33: `useFiles` has no pagination, no caching, no stale-while-revalidate

Every visit to the Files tab fires a full `listFiles` query. For 10,000 files, this is slow and wasteful.

### 34: The `Animated.Value` width animation on Home uses `useNativeDriver: false`

`Animated.timing(barAnim, { ..., useNativeDriver: false })`. For width animations, this can't use the native driver (RN doesn't support layout-property native driver). So the animation runs on the JS thread. For a 1s tween, fine. For something smoother, use `LayoutAnimation` or `react-native-reanimated`.

### 35: `feed.ts` `getHomeFeed` has unbounded result

```ts
.limit(limit); // default 6
```
Good, it's limited. But the underlying memberships query has no limit:
```ts
const { data: memberships } = await supabase
  .from('channel_members')
  .select('channel_id')
  .eq('user_id', userId);
```
If the user is in 5000 channels, this fetches all 5000 channel_ids. Add a `.limit(200)` or similar.

### 36: `useNotifications` realtime channel is mounted for the entire app session

`hooks/useNotifications.ts` line 27-53: the realtime channel is created when the user is signed in and persists for the entire session. For a long-running session with thousands of notifications, the channel accumulates state. Supabase handles this fine, but for battery / data, the channel is always on. **Verify** the channel actually unsubscribes on logout — looking at the cleanup, yes, `supabase.removeChannel(channel)` is called on unmount.

### 37: `useEffect` in `useFiles.ts` (called from `HomeScreen` and `FilesScreen`) duplicates the load

When the user visits Home, files are loaded. When they tap the Files tab, files are loaded again. Two requests for the same data. Not a bug, but caching would help.

### 38: No image optimization for thumbnails

`channels/[id].tsx` and `feed.ts` use `expo-image` (good, it has caching) but the thumbnails are loaded at full resolution from Supabase Storage. Cloudflare's image-resizing (`/width=200,height=300/`) would help. Or `expo-image` has `contentFit` and `transition` options to use.

## 7. Accessibility & UX

### 39: All TouchableOpacity buttons lack accessibility labels

Search for `accessibilityLabel` in the codebase: **0 occurrences.** Every button is text-only. Screen readers would announce "button" for everything. Add `accessibilityLabel` and `accessibilityRole` to key buttons.

### 40: No screen reader testing has been done

The app uses emoji as icons throughout (📡, 📂, 👤, 🛡️, etc.). These are decorative; screen readers might announce "satellite antenna" for the Channels tab. For a professional app, use `accessibilityElementsHidden` on decorative emoji and proper labels on the parent TouchableOpacity.

### 41: Form errors are shown via `Alert.alert` — disruptive

`Alert.alert('Error', err.message)` blocks the UI. For a form, this is jarring. Consider inline error messages.

### 42: No loading skeletons

Every list screen shows `<ActivityIndicator />` while loading. For a content app, skeleton placeholders (gray rectangles) feel more polished.

### 43: PaywallModal's "scroll hint" is text-only

`components/PaywallModal.tsx` line 187: `<Text>← scroll to see all plans →</Text>`. This works on Android but on iOS where the scroll indicators are subtle, users miss this. The snapToInterval gives haptic feedback on iOS, but on Android there's no visual cue beyond the text.

### 44: The `notifications` screen has no "no notifications" illustration

Just text. A small empty-state illustration would feel more polished.

### 45: Dark mode is hardcoded

`app.json` has `userInterfaceStyle: "dark"`. There's no light mode. For a professional app, this is a feature gap. Also, the theme is defined as constants, not a context, so adding a light theme means refactoring every screen.
